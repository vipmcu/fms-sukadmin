# Product Requirements Document (PRD)
## ระบบแจ้งซ่อมและขอใช้บริการออนไลน์ (Maintenance & Service Desk System)

---

### 1. บทนำและวัตถุประสงค์ (Objective)
ระบบแจ้งซ่อมและขอใช้บริการออนไลน์เป็นศูนย์กลางการรับแจ้งปัญหาอาคารสถานที่, โสตทัศนูปกรณ์, ระบบไฟฟ้า/ประปา, และการขอรับบริการไอทีของคณะ เพื่ออำนวยความสะดวกแก่อาจารย์ เจ้าหน้าที่ และนิสิต พร้อมระบบจ่ายงานช่าง ติดตามสถานะงานซ่อม และประเมินความพึงพอใจตามมาตรฐาน SLA

**เป้าหมายหลัก:**
1. รวมศูนย์คำร้องขอรับบริการและแจ้งซ่อมทั้งหมดไว้ในจุดเดียวแบบ One-Stop Helpdesk
2. มีการคำนวณกำหนดเวลาให้บริการตามมาตรฐาน (SLA Deadline) อัตโนมัติตามระดับความเร่งด่วนของปัญหา
3. จัดการจ่ายงานให้นายช่างผู้รับผิดชอบ และติดตามความคืบหน้าด้วยกระดาน Kanban Board แบบเรียลไทม์
4. เชื่อมโยงกับฐานข้อมูลห้องประชุม/ยานพาหนะ (`ReservationResource`) และทะเบียนครุภัณฑ์ (`AssetItem`)

### 2. กลุ่มผู้ใช้งานและสิทธิ์การเข้าถึง (User Personas & Roles)

| Persona / Role | คำอธิบายและบทบาทหน้าที่ | หน้าจอหลักที่ใช้งาน |
| :--- | :--- | :--- |
| **Requester (ผู้แจ้งซ่อม/ผู้รับบริการ)** | อาจารย์, เจ้าหน้าที่, หรือนิสิต ที่ต้องการแจ้งซ่อมอุปกรณ์หรือขอรับบริการ พร้อมแนบรูปถ่ายและติดตามสถานะ | Public & Staff Portal (`/helpdesk`, `/helpdesk/tracking`) |
| **Dispatcher / Helpdesk Manager (ผู้จ่ายงาน)** | หัวหน้างานอาคารสถานที่หรือหัวหน้างานไอที คัดกรองคำร้อง กำหนดความสำคัญ มอบหมายงานให้นายช่าง | Admin Console (`/maintenance/tickets`, `/maintenance/kanban`) |
| **Technician (นายช่าง/ผู้ปฏิบัติงาน)** | ช่างซ่อมบำรุงหรือเจ้าหน้าที่ไอที รับงาน บันทึกความคืบหน้า บันทึกการใช้อะไหล่ และส่งมอบงานซ่อม | Admin Console (`/maintenance/kanban`, `/maintenance/my-tasks`) |
| **System Administrator** | วิเคราะห์ Dashboard สรุปความถี่ของปัญหา อัตราการบรรลุ SLA และจัดการหมวดหมู่งานบริการ | Admin Console (`/maintenance/dashboard`, `/maintenance/settings`) |

### 3. ฟังก์ชันการทำงานหลัก (Functional Requirements)

#### RF-01: แบบฟอร์มแจ้งซ่อมด่วน (Quick Ticket Submission)
- ออกแบบให้ใช้งานง่ายบนสมาร์ทโฟน (Mobile-First):
  - เลือกหมวดหมู่งานบริการ: อาคารสถานที่, โสตทัศนูปกรณ์, ไอที/คอมพิวเตอร์, ยานพาหนะ
  - ระบุสถานที่เกิดเหตุ: เลือกห้องเรียน/ห้องประชุมจากฐานข้อมูล หรือระบุจุดภายนอก
  - แนบภาพถ่ายจุดที่ชำรุด/ข้อความแจ้งเตือน (สูงสุด 3 ภาพ)
  - กำหนดระดับความเร่งด่วน: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` (เช่น กระทบการเรียนการสอนทันที)
- ออกรหัส Ticket อัตโนมัติ (เช่น `SR-2026-0001`)

#### RF-02: การคำนวณและติดตาม SLA (Automated SLA Tracking)
- คำนวณกำหนดเวลาสิ้นสุด (`slaDeadline`) ทันทีที่เปิด Ticket:
  - `CRITICAL`: ต้องเริ่มดำเนินการภายใน 2 ชั่วโมง
  - `HIGH`: ภายใน 1 วันทำการ (24 ชม.)
  - `MEDIUM`: ภายใน 3 วันทำการ (72 ชม.)
  - `LOW`: ภายใน 7 วันทำการ (168 ชม.)
- แสดงแท็กสีเตือนเมื่อใกล้เกินเวลา (Near Breach) หรือเกินกำหนดเวลาแล้ว (SLA Breached)

#### RF-03: กระดานจัดการงานซ่อม (Kanban Work Order Board)
- แสดงคอลัมน์สถานะงาน:
  - `OPEN`: รอรับเรื่อง / รอจ่ายงาน
  - `ASSIGNED`: จ่ายงานให้ช่างแล้ว
  - `IN_PROGRESS`: ช่างกำลังเข้าดำเนินการซ่อม
  - `WAITING_PARTS`: รออะไหล่/จัดซื้อ
  - `RESOLVED`: ซ่อมเสร็จสมบูรณ์ พร้อมสรุปแนวทางแก้ไข
  - `CANCELLED`: ยกเลิกคำร้อง
- รองรับการลากย้ายการ์ดงาน (Drag & Drop) เพื่อเปลี่ยนสถานะ

#### RF-04: การประเมินความพึงพอใจและสถิติ (Rating & Satisfaction)
- เมื่อช่างปิดงาน ผู้แจ้งจะสามารถกดให้คะแนนความพึงพอใจ (1-5 ดาว) และความคิดเห็น
- Dashboard แสดงสถิติ: ร้อยละการปิดงานตาม SLA, หมวดหมู่ปัญหาที่พบบ่อย, อาคารที่แจ้งซ่อมสูงสุด

### 4. เกณฑ์การตรวจรับงาน (Acceptance Criteria)
- [ ] คำนวณ SLA Deadline อัตโนมัติถูกต้องตามระดับความเร่งด่วน
- [ ] ช่างต้องระบุ `resolutionNotes` ก่อนกดปิดงาน (`RESOLVED`) เสมอ
- [ ] หากแจ้งซ่อมระบุครุภัณฑ์ (`assetId`) ระบบต้องอัปเดตสถานะครุภัณฑ์เป็น `UNDER_REPAIR` อัตโนมัติ
- [ ] ประเมินความพึงพอใจได้ 1 ครั้งต่อ 1 ใบแจ้งซ่อมที่ปิดงานแล้วเท่านั้น
- [ ] ผ่านเกณฑ์ Quality Gate: TypeScript, Lint, Depcruise, Unit Tests 100%
